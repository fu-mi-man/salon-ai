# フェーズ1 MVP 実行トラッカー

このファイルはフェーズ1 MVP（口コミ返信管理）の**実行詳細の唯一の正本**である。
issue の一覧・起票順・依存・状態・受け入れ基準をすべてここに集約する。

- **戦略・全体像**は `docs/90_wiki/roadmap.md`（なぜ・フェーズ・spine）を見る。
- **実行（何を・どの順で・今どこまで）**は本ファイルを見る。
- `1行 = 1 GitHub issue ＝ 概ね 1 PR`。上から順に起票・着手すれば後戻りが最小になる。

## 再開時 同期チェック（着手前に必ず実行する）

このプロジェクトは数ヶ月空くことがある。**作業に入る前に、本トラッカーと現実（ドキュメント／GitHub／コード）がズレていないかを必ず確認し、ズレを先に直してから着手する。**

```bash
# 1) 作業位置の確認
git status
git log --oneline -10
git log --oneline -10 -- docs/   # docs の直近変更がコードに反映済みか後で確認する

# 2) 一覧 ↔ GitHub の整合（起票後）
gh issue list --state all --limit 100   # 本ファイルの「GH#」列・状態列と突き合わせる
gh issue list --milestone "Step 2" --state all   # Milestone 単位でも確認できる
```

確認観点（上から順に）:

1. **一覧 ↔ roadmap**：roadmap.md の Step 構成（Step 1〜7）と本ファイルの Step 見出しが一致するか。
2. **一覧 ↔ 仕様**：本ファイルが参照する仕様ファイル（`docs/02_specification/...` 等）が存在し、節がズレていないか。
3. **一覧 ↔ GitHub**：本ファイルの「GH#」が実 issue 番号と一致し、「状態=✅」の issue が closed になっているか。
4. **一覧 ↔ コード**：「状態=✅」の issue が実際にコードへ反映されているか主要ファイルをスポット確認する（`web/src/app/dashboard/page.tsx` / `supabase/migrations/` / `web/src/app/login/` など）。
5. **仕様 ↔ コード**：`git log -- docs/` の直近変更がコードに反映済みか。未反映なら新規 issue 化を検討する。

**ズレを見つけたら、本ファイルの「状態」「GH#」列または該当ドキュメントを先に更新してから実装に入る。**

## 凡例

- 状態: ⬜ 未着手 ／ 🟡 着手中 ／ ✅ 完了
- GH#: 起票後に GitHub issue 番号を記入する
- ラベル: `enhancement`（機能）／ `infra`（デプロイ・CLI・DB基盤）／ `test`（テスト）／ `docs`（文書）
  - リポジトリには現状 `enhancement` / `bug` のみ。`infra` / `test` / `docs` は起票前に追加しておく（任意）。
- Milestone: GitHub の Milestone を Step 1〜7 で作成し、各 issue に割り当てる。

## 全体の依存フロー

```text
Step0 全画面UIプロトタイプ（静的・本物ルート・インフラ不要）
   └→ Step1 ダッシュボードの操作（ダミー状態）
          └→ Step2 認証 + 全スキーマ一括 + 早期デプロイ + E2E基盤
                 ├→ Step3 スタッフ・例文（DB投入＋連携）
                 └→ Step4 履歴の永続化
                        └→ Step5 Gemini生成（要 Step3 例文 / Step4 保存先）→【E2E②】
                               └→ Step6 AI修正（Step1のダミーUIを本実装に差し替え）
                                      └→ Step7 運用開始準備
```

スキーマは **Step2（2-2）で `docs/01_requirements/03_data.md` 通りに全テーブルを1回で作成する**。
このため「Step3/Step4 でのテーブル追加・FK後付け・型再生成」は本計画には存在しない（→ 末尾「方針メモ」参照）。

## 方針メモ（なぜこの構成か）

旧 `docs/00_issues/stepN_*.md` ドラフトは方針見直し前に書かれていた。本トラッカーはそれらを統合し、以下を反映している。

1. **スキーマは Step2（2-2）で一括作成**：旧ドラフトはテーブル作成を Step2/3/4 に分散し、`salon_users.staff_id` を「NULL で作って後で FK 追加」していた。本計画では一括作成＋FK＋RLS とし、段取り依存の事故を排除した。
2. **デプロイ前倒し（2-8）**：旧ドラフトは Step7 で初めてデプロイ。本計画では認証スケルトン完成時に早期デプロイし、以降は継続デリバリ。Step7 は初期アカウント発行・本番確認に縮小。
3. **前提issueの追加**：`/` テンプレ掃除（0-1）・Supabase CLI 導入（2-1）・初期 seed（2-3）・Playwright 基盤（2-9）を新設（旧ドラフトは存在しない基盤を前提にしていた）。
4. **E2E は2点に集約**：①認証フロー（2-10）と ②生成happy path（5-5）。旧ドラフトのように各 Step には置かない。
5. **正本の一本化**：旧 `stepN_*.md`（7本）は本ファイルに統合済み。詳細はすべて本ファイルを参照する。
6. **Step0 を新設（全画面UIプロトタイプ）**：本物のルート（`/dashboard`・`/login`・`/reset-password`）に shadcn/Tailwind で静的UIを先に作り、以降の Step が振る舞い・ロジックを乗せる。捨てUIにしないため本番除外は不要。旧 Step1（UI一括）は Step0（静的）＋Step1（操作）に分割した。コンポーネントは中庸（shadcnプリミティブ＋返信カードのみ抽出）。
7. **owner 単一運用に絞る（staff 個別ログインは後続）**：フェーズ1は owner ログインのみ実装。RLS の role 権限差・staff ロールのUI出し分け・staff 発行手順は作らない。スタッフ・例文は管理UIを作らず DB 直接投入する（`03_data.md` の方針通り）。これにより Step3 はスタッフCRUD UI を廃し「seed 投入＋選択連携」に縮小。Step2 に初期 seed（2-3）を追加し、デプロイ後・生成系の検証を可能にした。RLS は `salon_users.user_id = auth.uid()` 起点（`04_non-functional.md` の旧例の誤りを修正）。
