# 実装ロードマップ

ソースコードを「生きた仕様書」として扱い，詳細設計書の作成を最小限にしながら動くものを早く届ける方針。

このファイルは**戦略・全体像（なぜ・どのフェーズで・どの順序で）**を担う。
**実行詳細（issue 一覧・受け入れ基準・進捗状態）は GitHub（issues・Project #3）が唯一の正本**とする。Step 間の依存フローと構成の意図は `docs/00_issues/README.md` を見る。

コアの価値フロー：

```text
オーナーがサロンボードの口コミをコピー
  → Web UIに貼り付け・スタッフ選択
  → Gemini（few-shot プロンプト）→ Supabase に履歴保存
  → オーナーが返信文をコピーしてサロンボードにペースト
```

## フェーズ1 MVP（口コミ返信管理）

### 進め方の方針（spine）

「まず全画面を絵で作って見せ，あとから1画面ずつ厚くする」方針。手戻りと事故を減らすため次の4点を組み込む。

- **Step0 で全画面の静的プロトタイプを本物のルートに作る**：`/dashboard`・`/login`・`/reset-password` を，本番で使う技術（shadcn/ui・Tailwind v4）でハードコード・リンク遷移のみで作る。捨てUIにせず，以降の Step がこの上に振る舞い・ロジックを乗せる。本番除外は不要（デプロイは Step2 から，認証導入で自然に本番画面になる）。コンポーネントは中庸（shadcn プリミティブ＋繰り返す返信カードのみ抽出）。
- **スキーマは Step2 で一括作成**：データモデル（`docs/01_requirements/03_data.md`）は確定済みなので，全テーブルを1回で作る。Step ごとにテーブルを足したり FK を後付けしない。
- **デプロイ前倒し**：認証スケルトンが通った時点（Step2）で一度本番に上げ，以降は継続デリバリにする。
- **E2E はキリのいい2点に集約**：①認証フロー（Step2），②生成happy path（Step5）。

```text
Step0 全画面UIプロトタイプ（静的・本物ルート）
   └→ Step1 ダッシュボードの操作（ダミー状態）
          └→ Step2 認証 + 全スキーマ一括 + 早期デプロイ + E2E基盤
                 ├→ Step3 スタッフ・例文（DB投入＋連携）
                 └→ Step4 履歴の永続化
                        └→ Step5 Gemini生成 →【E2E②】
                               └→ Step6 AI修正
                                      └→ Step7 運用開始準備
```

### Step 0 — 全画面UIプロトタイプ（静的）

`/dashboard`・`/login`・`/reset-password` を，本物のルートに静的UIとして作る。ハードコードのダミーデータ・リンク遷移のみで，操作やロジックは持たせない。まず全体像を絵で確認する。

### Step 1 — ダッシュボードの操作（ダミー状態）

Step0 で作ったダッシュボードの静的UIに振る舞いを乗せる（コピー・削除・編集モードのAI修正ダミー・ページネーション・入力非活性制御）。Supabase 不要・ダミー状態で動かす。`docs/02_specification/screens/01_dashboard.md` 参照。

### Step 2 — 認証・スキーマ基盤・早期デプロイ

`docs/90_wiki/setup/05_supabase.md` の構成に従い，認証基盤と全テーブル（`docs/01_requirements/03_data.md`）を用意し，検証用の初期 seed（サロン/店舗/owner）も入れる。Step0 で作ったログイン/リセットの静的UIに認証ロジックを配線する。フェーズ1は **owner ログインのみ実装**（staff 個別ログインは後続フェーズ）。招待機能や詳細権限管理 UI は入れない。認証が通った時点で Vercel に早期デプロイする。

### Step 3 — スタッフ・トーン例文（DB投入＋連携）

スタッフ・返信例文は管理UIを作らず DB 直接投入する（`docs/01_requirements/03_data.md` の方針）。ダッシュボードのスタッフ選択を DB 連携に切り替える。

### Step 4 — 履歴の永続化（Server Actions）

`review_replies` の取得・更新・削除を Server Actions 経由で永続化し，30日後の自動削除（pg_cron）を設定する。

### Step 5 — Gemini 連携（返信文生成）

Server Action から Gemini API を呼び出して返信文を生成する。選択スタッフのトーン例文を few-shot として組み込む。プロンプト仕様は `docs/02_specification/integrations/gemini.md` を参照。

### Step 6 — AI修正（編集モードでの再生成）

編集モード内で修正指示を与えて返信文を書き換える。Step1 で用意したダミー UI を本実装に差し替える。

### Step 7 — 運用開始準備

友人の美容室への引き渡しに向け，初期アカウント発行手順のドキュメント化と本番動作確認を行う（デプロイ自体は Step2 で前倒し済み）。
